# Authorize by acting role and resource relationship

A User may hold multiple roles but must choose an acting role for each workspace and request; the server validates that role and records it with the User in the audit history. Authorization combines that role with resource relationships rather than granting broad access by role name alone: Students access themselves, Teachers access only assigned sessions and limited roster data from assignment until 48 hours after session end, Organization Managers access only time-bounded reporting for their sponsored students, and Platform Administrators hold marketplace-wide operational authority. This explicit context prevents a multi-role User from accidentally exercising broader authority and keeps teacher and employer data boundaries enforceable in every GraphQL resolver.

Authentication is delegated to Auth0 through a replaceable OpenID Connect adapter that maps an external issuer and subject to an internal User. Auth0 proves who signed in, while the application database remains authoritative for roles, Organizations, and resource relationships rather than adopting provider-specific B2B authorization; tests replace the provider boundary with a controlled fake.

Every resolver and worker command uses a mandatory TypeScript policy layer with verified User and acting-role context; policy-aware services scope queries by assignment, Sponsorship, and time window. PostgreSQL Row-Level Security is not used initially because duplicating these contextual rules in SQL would create a second policy system and complicate pooled connections, administrator access, and system workers. PostgreSQL enforces structural integrity, while integration tests exercise the application policy against real data, including cross-Organization and nested-field attempts.

Requests for private resources outside the caller's relationship scope return Not Found so identifiers cannot be used to confirm unrelated students, teachers, Organizations, feedback, or reports. Forbidden is reserved for operations on resources already legitimately visible to the caller; the audit history retains the actual denial reason.
