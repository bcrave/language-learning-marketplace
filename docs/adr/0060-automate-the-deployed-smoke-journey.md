# Automate the deployed smoke journey

The deployed smoke journey runs automatically as the last stage of every release rather than as a manual check after it. It authenticates as all four shared identities — Student, Teacher, Organization Manager, and Platform Administrator — and walks each one's journey: authentication and Interface Locale, Class Session Discovery, Booking and Student Cancellation, the anonymous public Teacher Profile, the assigned Class Roster and one permitted Teacher action, the Organization Manager's scoped reporting, one representative Platform Administrator operation, the cross-role replays those journeys must be refused, and the Audit Entries every mutation leaves behind. A failed journey fails the release job, which is the owner-attention route for deployment incidents.

Every state-changing step is a matched pair that asserts the reading it started from — book and cancel, add and remove an Availability Exception, credit and debit the same Class Credit. The [Security Release Gate](../security-verification.md) asks the suite to use disposable fixtures and not to depend on mutable reviewer state; a journey that left its own changes behind would instead depend on its previous run's, and the second release of the day would fail for reasons belonging to the first.

The four identities are what make the cross-role denials evidence rather than assertion. A per-role journey can only show that a role reaches what it should; replaying one journey's identifiers under another role is the only way to show it does not reach what it should not, and that needs a second credential holding genuinely different authority. This widens what ADR 0039 releases into the protected `production` environment from two shared credentials to four; the reasoning below is unchanged, because all four are bounded to their manifest roles in exactly the same way.

This amends two earlier decisions. [ADR 0037](0037-isolate-fake-authentication-from-production.md) gave Auth0 "a small manual deployed smoke test"; a manual step cannot fail a release closed, and the [Security Release Gate](../security-verification.md) requires evidence that is neither missing nor unexplained. [ADR 0039](0039-separate-public-client-configuration-from-secrets.md) held that GitHub's protected `production` environment contains only an environment-scoped deployment token; automating the journey adds one release-scoped Auth0 principal and the shared identities' credentials to that environment. Everything else ADR 0039 decides is unchanged: the database credential stays a Railway reference variable, the migrations, identity binding, and readiness gates moved into Railway pre-deploy commands inside the private network precisely so no database credential reaches GitHub, and the release job's output remains redacted evidence carrying check names, codes, and counts.

The residual risk is accepted rather than dismissed. The smoke principal can sign in as the shared demonstration identities, so it reaches exactly what a reviewer reaches and nothing more: those identities are bounded to their manifest roles, hold no Project Owner elevation path, and govern only synthetic people. Its credentials are released for one run under Project Owner approval, are never printed — a provider refusal reports only its status code — and are rotated rather than preserved if they appear outside the protected environment. The journey uses the resource-owner password grant, which is the release job's own principal and not a browser path; [ADR 0027](0027-keep-spa-auth-tokens-in-memory.md) continues to govern how a reviewer's own session authenticates, and the redirect-based Authorization Code Flow with PKCE remains asserted in the client configuration and exercised by manual verification, because no automated agent can drive a real Auth0 redirect without becoming a second, weaker authentication path.
