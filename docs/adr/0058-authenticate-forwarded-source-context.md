# Authenticate forwarded source context with a shared proxy secret

Caddy discards every inbound forwarding header, then presents the address it verified in `X-Verified-Source` and proves it is Caddy with `X-Proxy-Authorization`, a deployment secret the API holds as `API_TRUSTED_PROXY_SECRET` and compares in constant time before keying [ADR 0025](0025-bound-public-api-resource-consumption.md)'s per-source limits on that address. Context that is absent, unauthenticated, chained, or not a single address fails closed with HTTP 403 rather than falling back to the socket peer, which behind the [single public origin](0028-use-a-single-public-origin.md) is Caddy itself and would collapse the entire internet into one budget. Refusals are counted against the connection they arrived on, so a misconfigured origin cannot buy an unbounded path. The limiter continues to key on a salted hash, so no source address is retained. Liveness and readiness are probed over private networking rather than through Caddy, so those two routes key on the connection instead; [ADR 0038](0038-deploy-api-first-and-frontend-last.md) verifies the API before the public origin exists at all.

Railway private addresses are dynamic, so allowlisting the peer is unavailable and the shared secret is the only in-application evidence of which peer connected. Trusting `X-Forwarded-For` instead was rejected as worse than the original defect: a caller could vary the header per request and mint a fresh budget every time. Production requires the secret; without one configured the API keys on the connection's own address, which is what local development and the browser suite need. Rotation deploys Caddy and the API together and a mismatch stops public traffic, which is accepted because the alternative silently downgrades a per-source control to a global cap.
