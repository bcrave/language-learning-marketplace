# Keep core booking changes in one PostgreSQL transaction

Booking, seat allocation, schedule-conflict validation, and Class Credit deduction share one PostgreSQL transaction in a modular monolith because they form one business commitment and must succeed or fail together. Booking mutations require a client-generated idempotency key: retrying the same request returns its original outcome, while reusing the key for different request details is rejected. Application checks provide useful errors, while PostgreSQL remains the concurrency guard through locked session and credit-account rows plus constraints against duplicate bookings, schedule overlaps, over-capacity sessions, and negative balances. Student Bookings and Teacher assignments create shared schedule-commitment records containing the User and immutable session interval; a PostgreSQL exclusion constraint rejects overlapping active ranges across roles. Each session stores an occupied-seat counter that is incremented or decremented with its Booking change under the row lock, constrained between zero and Seat Capacity, and reconciled against active Booking history. A cancellation commits its refund and seat release first, then a durable event starts retry-safe, ordered waitlist promotion through the same booking path. A candidate whose eligibility has changed is closed with the specific business reason before promotion continues to the next candidate; a temporary system failure instead preserves queue position and retries. Waitlist Withdrawal and promotion serialize on the same entry: withdrawal wins if it commits first, while promotion wins if its Booking commits first, after which the Student must use Student Cancellation. Events and notifications are emitted only after commit; separating core responsibilities into asynchronously consistent services would require compensating actions and expose contradictions without a justified scale requirement.
