# Evaluate private alerts inside the API

The operator guide's application-detected thresholds are evaluated by a watch running in the API process, on the guide's own 30-second probe interval. Each reading is a plain snapshot of state that already exists — database reachability and applied schema, the worker heartbeat, runnable and exhausted Graphile jobs, the maintenance lease and fixture generation, the latest Canonical Data Rebuild outcome, rolling-fixture reconciliation, exhausted Notification Intents, and in-process aggregate counters for refusals, denied authorizations, and observed Auth0 failures. Nothing is written to make observation possible. The incident lifecycle of [ADR 0022](0022-use-lightweight-correlated-observability.md) — one confirmation alert, one more if severity rises, one recovery notification, and no reminders — lives in an `operational_incidents` table, because the process that dispatches restarts during exactly the incidents it must remember. Alerts leave as ordinary privacy-filtered Sentry events, which is the owner-controlled email route the guide already names; no new outbound integration and no owner endpoint is introduced.

The API is the only process that can hold this. A stale worker heartbeat is one of the conditions, so a watch inside the worker would fall silent precisely when it mattered; a separate watcher service would be a third container against a $15 monthly ceiling. The conditions the API cannot raise for itself are marked as such in the policy and answered elsewhere: its own liveness is Railway's restart policy, and deployment, backup, and drill failures are GitHub Actions job failures. Sentry failure patterns and the Railway cost ceiling stay with their providers, and the policy records their thresholds so provider configuration can be checked against them rather than remembered. A fourth kind is recorded honestly rather than pretended away: a secret leaving its approved store, an authorization that failed open, an unauthorized mutation that committed, and a credential rejection that suggests revocation have no automated detector anywhere in this deployment. They are found by the Security Release Gate's abuse cases or by a person, and the policy carries their containment, evidence, and clearing rule so the response is not improvised. Where a clearing rule ends in a smoke journey only a person can run, the incident stays open until the owner records having run it through the diagnostics workflow, which sends its single recovery notification. The one incident the durable store cannot hold is PostgreSQL being unreachable, because the store is PostgreSQL; that single condition keeps its lifecycle in memory so an outage still sends one alert and one recovery.

The Node Sentry SDK runs with automatic instrumentation off. Its default integrations install an OpenTelemetry stack into the process — the collector-shaped overhead ADR 0022 declined — and attach request and query detail this project would then filter back out. Unhandled failures and explicit reports are what the owner acts on; [ADR 0043](0043-verify-accessibility-with-automation-and-manual-review.md)-style browser traces remain enabled in the bundle at a low sample rate. Both halves of the deployment run every event through one shared allowlist filter rather than a denylist, so a field nobody added deliberately is dropped rather than disclosed, and the alert evidence a condition may carry is drawn from that same allowlist. The watch writes no Audit Entry: `CONTEXT.md` scopes those to authenticated mutations, denied sensitive-data reads, and background actions that change marketplace state, and the guide says outright that alerts do not create Audit Entries merely for alerting.
